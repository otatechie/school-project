# GovPay Desk — Technical Documentation

Architecture, data model, routes and conventions for developers working on the
codebase. For how to *operate* the system, see [USER-GUIDE.md](USER-GUIDE.md).

---

## 1. Stack

| Layer | Technology |
|---|---|
| Backend | Laravel 12, PHP 8.2+ |
| Frontend | React 19 + TypeScript, via Inertia 2 |
| Styling | Tailwind CSS 4, shadcn/ui (Radix primitives) |
| Build | Vite 7 |
| Auth | Laravel Fortify (incl. two-factor) |
| Routing helpers | Laravel Wayfinder — generates typed route helpers into `resources/js/routes/` and `resources/js/actions/` |
| Charts | Recharts |
| Database | SQLite by default (`DB_CONNECTION=sqlite`) |
| AI | `anthropic-ai/sdk` — Claude API, optional |
| Tests | Pest 4 |
| Formatting | Pint (PHP), Prettier + ESLint (TS) |

There is no separate API layer — every page is an Inertia response rendered by a
controller. The two AI endpoints are the only JSON responses.

## 2. Getting started

```bash
composer install
npm install
cp .env.example .env
php artisan key:generate
php artisan migrate:fresh --seed
composer dev          # server + queue + logs + vite, concurrently
```

Then open http://127.0.0.1:8000.

### Seeded accounts

All seeded accounts use the password `password`.

| Email | Role | Purpose |
|---|---|---|
| `ota@example.com` | Administrator | Full access; can approve own vouchers |
| `ama@example.com` | Finance Officer | Prepares, submits, pays |
| `kofi@example.com` | Finance Officer | Same |
| *(2 generated users in Administration)* | Approver | Approve/reject others' vouchers |
| *(4 generated users in Procurement)* | Viewer | Read-only |

The approver and viewer accounts are generated by factory, so their emails vary
per seed — look them up with `php artisan tinker` or the Users page. To walk the
core loop, sign in as `ama@example.com` to prepare and submit, then as
`ota@example.com` to approve.

### Optional: AI features

```env
ANTHROPIC_API_KEY=sk-ant-...
ANTHROPIC_MODEL=claude-opus-5     # default
ANTHROPIC_TIMEOUT=45              # seconds, default
```

Without a key every AI feature reports itself unavailable and the rest of the
application is unaffected. See section 8.

## 4. Data model

### Migration history

| Migration | Contents |
|---|---|
| `0001_01_01_*` | users, cache, jobs (framework defaults) |
| `2025_08_14_170933` | two-factor columns on users |
| `2026_01_27_092633` | staff/approval fields on users |
| `2026_01_27_093232` | departments |
| `2026_01_27_153134` | payment_vouchers, voucher_documents, voucher_approvals |
| `2026_01_28_164205` | memos |
| `2026_08_03_095100` | drops unused MVP tables and columns |
| `2026_08_08_100000` | `role` on users; accounts, ledger_entries, documents, system_logs, app_notifications |

**Read `2026_08_03_095100` before trusting the January migrations.** It drops
`voucher_documents` and `voucher_approvals` entirely (their models
`VoucherDocument` and `VoucherApproval` are also deleted), along with
`users.last_login_at`, `last_login_ip`, `approval_level`, `approval_limit`,
`password_changed_at`, `payment_vouchers.internal_notes` and `memos.printed_at`.

Document storage is now the polymorphic `documents` table; approval state lives
on the voucher row itself.

One inconsistency to be aware of: `PaymentVoucher::$fillable` still lists
`internal_notes`, whose column was dropped. It is never written to, so nothing
breaks, but it is a dead entry.

### Core tables

**`payment_vouchers`** — the central record.

| Group | Columns |
|---|---|
| Identity | `voucher_number` (unique), `voucher_date` |
| Payee | `payee_name`, `payee_account_number`, `payee_bank`, `payee_phone` |
| Payment | `description`, `amount` (decimal 15,2), `payment_method`, `cheque_number`, `payment_reference` |
| Budget | `budget_line`, `budget_code`, `department_id` |
| State | `status` — `draft` \| `pending` \| `approved` \| `rejected` \| `paid` |
| Actors | `created_by`, `approved_by`, `rejected_by`, `paid_by` |
| Timing | `submitted_at`, `approved_at`, `rejected_at`, `paid_at` |
| Notes | `rejection_reason` |

`department_id` and `created_by` use `restrictOnDelete` — a department or user
with vouchers cannot be deleted, preserving the historical record.

**`memos`** — `memo_number` (unique), `memo_date`, `subject`, `body`, `to_name`,
`to_designation`, `from_name`, `from_designation`, `department_id`, nullable
`voucher_id`, `created_by`, `status` (`draft` | `finalized` | `printed`).
There is no `printed_at` — it was created then dropped, so "printed" is only a
status, with no timestamp recording when.

**`accounts`** — `code` (unique), `name`, `type` (asset/liability/equity/revenue/expense), `is_active`.

**`ledger_entries`** — one row per side of a double entry: `reference`,
`entry_date`, `account_id`, `description`, `debit`, `credit`, nullable
`payment_voucher_id` (the origin document), `created_by`.

**`documents`** — polymorphic (`documentable_type` / `documentable_id`): `name`,
`path`, `mime_type`, `size`, `uploaded_by`.

**`system_logs`** — `action`, `description`, polymorphic subject, `user_id`,
`ip_address`. Append-only by convention; nothing in the app updates or deletes.

**`app_notifications`** — `user_id`, `type`, `title`, `body`, `link`, `read_at`.

### Reference-number generation

Both voucher and memo numbers are generated per year by reading the last record
and incrementing its trailing three digits:

```php
'PV-'   . date('Y') . '-' . str_pad($sequence, 3, '0', STR_PAD_LEFT)
'MEMO-' . date('Y') . '-' . str_pad($sequence, 3, '0', STR_PAD_LEFT)
```

This is read-then-write with no lock or unique retry, so two simultaneous
creations can collide on the unique index. Acceptable at this scale; replace
with a sequence table or a retry on constraint violation before real concurrent
use.

## 5. Authorization

All authorization for vouchers lives in
[PaymentVoucherPolicy.php](../app/Policies/PaymentVoucherPolicy.php). Roles are
constants on `User` (`admin`, `approver`, `finance_officer`, `viewer`), fixed in
code — there is no roles table.

| Ability | Requires status | Requires role | Extra |
|---|---|---|---|
| `viewAny` | — | any | user must be active |
| `create` | — | admin, finance officer | |
| `update` | draft or rejected | admin, finance officer | |
| `delete` | draft | admin, finance officer | |
| `submit` | draft | admin, finance officer | |
| `review` | pending | admin, approver | **preparer cannot review own unless admin** |
| `markPaid` | approved | admin, finance officer | |

Two invariants are worth stating explicitly because the whole design rests on
them:

1. **Immutability after approval.** `update` returns false for any status other
   than `draft` or `rejected`, so approved and paid vouchers cannot be edited.
   `VoucherPolicyTest` asserts this against the route, not just the policy.
2. **Separation of duties.** `review` returns false when
   `$voucher->created_by === $user->id` unless the user is an admin.

Memos, users, departments and ledger pages have **no policy**. They are gated
only by the `auth` + `verified` middleware, so any authenticated user can reach
them. If role-gating those areas matters, that is new work.

## 6. Request lifecycle: draft → paid

```
store()      → status draft, created_by = actor, number generated
               → AuditLogger 'voucher.created'

submit()     → authorize('submit') → status pending, submitted_at = now
               → AuditLogger 'voucher.submitted'
               → Notifier::toApprovers(...)

review()     → authorize('review') → approve: status approved, approved_by/_at
                                     reject:  status rejected, rejected_by/_at,
                                              rejection_reason (required)
               → AuditLogger 'voucher.approved' | 'voucher.rejected'
               → Notifier::toUser(creator, ...)

markPaid()   → authorize('markPaid') → status paid, paid_by/_at
               → LedgerPoster::post($voucher->refresh())
               → AuditLogger 'voucher.paid'
               → Notifier::toUser(creator, ...)
```

`markPaid` calls `refresh()` before posting because `LedgerPoster` reads
`status` and `paid_at` off the model and would otherwise see stale values.

## 7. Services

### `LedgerPoster`

Posts a paid voucher as a balanced double entry inside a transaction:

```
Dr  expense account   (mapped from budget_line)
Cr  1100 Cash | 1200 Bank   (from payment_method)
```

Three guards, in order: it returns early unless `status === 'paid'`; it returns
early if a `LedgerEntry` already exists for the voucher (**idempotency** — this
is why re-seeding does not duplicate); and it returns early if either account
lookup fails.

Budget lines are free text, so `BUDGET_LINE_ACCOUNTS` maps substrings to codes
with `str_contains`, falling back to `5900 General Expenses`:

| Substring | Code |
|---|---|
| office supplies, stationery | 5100 |
| salaries, payroll | 5200 |
| travel, transport | 5300 |
| utilities | 5400 |
| maintenance | 5500 |
| *(no match)* | 5900 |

Settlement: `bank_transfer` → `1200`, everything else → `1100`.

**To extend:** add to `BUDGET_LINE_ACCOUNTS` and ensure the account exists in the
seeder. The structurally correct fix is to replace the free-text `budget_line`
with a foreign key to `accounts`; the string mapping is a deliberate MVP
shortcut.

### `AuditLogger`

`AuditLogger::record($action, $description, ?$subject)` writes a `SystemLog` row
with the authenticated user and request IP. Static, no interface, called
directly from controllers.

### `Notifier`

`Notifier::toUser(...)` creates one `AppNotification`. `Notifier::toApprovers(...)`
fans out to every **active** user with role admin or approver. In-app only — no
mail, no queue.

### `VoucherIntelligence`

See section 8.

## 8. AI features

[VoucherIntelligence.php](../app/Services/VoucherIntelligence.php) wraps the
Claude API for two advisory features. The governing design rule is that **AI is
an assist, never a dependency** — every path degrades to null and the caller
falls back to the manual flow.

**`isEnabled()`** — true only when `config('anthropic.api_key')` is filled.
Controllers pass this to the frontend as `aiEnabled` so the UI can hide or
explain the feature.

**`reviewVoucher(PaymentVoucher): ?array`** — loads the last 20 paid vouchers
from the same department as context and asks Claude to flag anything an approver
should check. Returns `{risk: low|medium|high, summary: string, findings: string[]}`.

**`draftMemo(PaymentVoucher): ?array`** — drafts a memo subject and body from a
paid voucher. Returns `{subject: string, body: string}`.

Both use structured output (`outputConfig` with a JSON schema), so the response
shape is enforced by the API rather than parsed hopefully. Both prompts
explicitly instruct the model to use only the supplied facts and not to invent
references, dates or signatories.

Failure handling: every call is wrapped in `try/catch(Throwable)`. A thrown
exception, a `refusal` stop reason, or a non-array decode all log a warning and
return null. The controller then returns `{available: false, message: ...}`,
distinguishing "not configured on this deployment" from "temporarily
unavailable".

Endpoints:

| Route | Auth | Notes |
|---|---|---|
| `POST /payment-vouchers/{voucher}/ai-review` | `authorize('review')` | Logs `voucher.ai_reviewed` on success |
| `POST /memos/ai-draft/{voucher}` | voucher must be `paid` | Logs `memo.ai_drafted` on success |

**Known gap:** `ai-draft` has no frontend caller. Wayfinder has generated route
helpers for it, but no component on `memos/create.tsx` invokes them, so memo
drafting is unreachable from the UI. `ai-review` *is* wired, on
`payment-vouchers/pending.tsx`.

**Note that `ai-draft` is authorized only by voucher status**, not by policy or
role — any authenticated user can spend an API call against any paid voucher.
Worth tightening if the key is production-billed.

## 10. Frontend

Pages live in `resources/js/pages/` mirroring route names — `payment-vouchers/pending.tsx`
serves `payment-vouchers.pending`. Controllers name them explicitly in
`Inertia::render()`.

Navigation is defined statically in
[app-sidebar.tsx](../resources/js/components/app-sidebar.tsx), in three groups:
Financial Operations, Reports & Documents, Administration. **The sidebar does not
consult roles** — every authenticated user sees every link, and authorization is
enforced server-side when the action is attempted.

### UI conventions

Match these when adding pages:

- **Say a thing once.** Page title, card title and section heading should not
  repeat each other. A status badge on a page already filtered to that status
  adds nothing.
- **Card padding is set once**, on `<Card className="py-5">`. Do not add `pt-6`
  to `CardContent` — shadcn's `Card` already has `py-6` and the two stack into a
  dead band.
- **Form spacing scale:** `space-y-5` between sections, `space-y-2` heading to
  fields, `gap-y-3.5` between field rows, `space-y-1.5` label to input.
- **Money** is right-aligned, `tabular-nums`, two decimals, em-dash for zero.
  Tables showing money show totals.
- **Every list** needs an empty state that distinguishes "nothing here yet" from
  "nothing matches your filter", and offers a way out of the filter.
- **Every paginated list renders pagination.** A count reading "10 of 13" with no
  way to reach the other 3 is a bug.
- **Errors** appear inline *and* in a summary at the top of long forms, each
  summary line linking to its field.
- **Dates** use `en-GB` formatting (`3 August 2026`).
- **Colour is never the only signal** — pair it with an icon or text.

## 11. Querying conventions

Index controllers follow a consistent shape: `when($request->filled(...))`
filters, `latest()`, `paginate()`, `withQueryString()`, and a `filters` prop
echoing `$request->only([...])` so the UI can render current filter state.

Two things to be aware of:

- **Search is `LIKE`-based and unindexed.** Fine at this data size; it will not
  scale.
- **`LedgerController::transactions` and `FinancialReportController` use SQLite
  functions directly** — `strftime('%m', paid_at)`, `strftime('%Y', paid_at)`.
  These will break on MySQL or Postgres. Porting the database means rewriting
  those aggregates.
- `LedgerController::transactions` computes totals over the **whole filtered
  set** with a second query, not just the visible page — duplicating the filter
  chain. If you change one filter, change both.

## 13. Known gaps and technical debt

Ordered roughly by how likely each is to bite:

1. **Documents cannot be uploaded.** The `documents` table, `Document` model and
   index page exist; there is no store endpoint, no file handling, no validation.
   Records only appear via the seeder.
2. **AI memo drafting is unreachable** from the UI (section 8).
3. **`ai-draft` is not role-authorized** — status check only.
4. **No policies outside vouchers.** Memos, users, departments and ledgers are
   gated only by `auth`.
5. **Reference-number generation can race** (section 4).
6. **SQLite-specific date SQL** in reports and ledger queries (section 11).
7. **Ledger is one-directional** — no manual journals, no reversals, no period
   close. A mistaken payment cannot be corrected in the ledger.
8. **`budget_line` is free text**, mapped by substring. Should be a foreign key.
9. **Search is unindexed `LIKE`.**
10. **Admin-created users get `password`** with no invite or reset flow.
11. **Memos cannot be edited or deleted**, and produce no printable output.
12. **No `payment-vouchers.show` route.**
13. **GIFMIS is not implemented** and has been removed from the codebase.
14. **Dead `internal_notes` entry** in `PaymentVoucher::$fillable` for a column
    that no longer exists (section 4).
